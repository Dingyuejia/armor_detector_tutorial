# 从零写到能打：五件事

骨架能连上仿真、能取帧、能发指令，但中间是空的：`detect()` 返回空，
`estimate()` / `command()` 返回空结构体。所以**每个场景的命中都是 0**。

把下面五件事做完，这条链路才成立。按顺序做，不要跳——每一件都下一件的前提。

| | 做完之后该看到什么 | 验收命令 |
|---|---|---|
| S0 检测 | `ideal_samples` 由红变绿 | `ctest --test-dir build -R ideal_samples` |
| S1 距离与弹道 | `far` 从 0 到有 | `bench/run.sh far 8` |
| S2 关联与状态估计 | `spin` 的指令稳定 | `bench/run.sh spin 8` |
| S3 提前量 | `translate` 从 0 到有 | `bench/run.sh translate 8` |
| S4 生命周期 | 目标消失后停火 | 见 S4 |

---

## 指标口径（先读这一节，后面都用它）

**主指标是命中/秒**（`hit / 运行秒数`），不是命中率。命中率会被"很少开火但很准"
骗过去：只打 6 发中 4 发，命中率 0.67，看着比谁都好。命中/秒同时惩罚"打不准"
和"不敢打"。

**每跑一轮先看两个健康指标**，`bench/report.py` 会对异常的那一轮告警：

- **帧率**：低于 40 说明这台机器当时跑不动，闭环带宽跟着掉，命中/秒会莫名其妙变低。
- **仿真/墙钟**：仿真时间 / 真实时间，理想 1.00。明显低于 1 说明仿真掉步。

这两项不对，那一轮的数字直接作废，重跑——**不要**把它当成自己的 bug 去查。

**噪声**：同一份二进制重复跑同一个场景，命中/秒本身就会抖。动态场景 15~30%
都算正常，粗糙的实现能抖到"0 到 1.9"。所以：

- `0.40 → 0.45` 不能当改进的证据；
- 想下结论至少重复 3 次取中位数——这就是你要造的第一个工具。

**参照点**（命中/秒，8 秒单次，同一台机器）。`solution` 分支是同一道题的完整实现：

| 场景 | 条件 | 骨架 | `solution` |
|---|---|---:|---:|
| `static` | 4 m 静止 | 0.00 | 6.88 |
| `lowlight` | 4 m，0.15× 曝光 | 0.00 | 6.50 |
| `far` | 5.5 m 静止 | 0.00 | 9.00 |
| `translate` | 5.5 m，1.5 m/s 横移 | 0.00 | 3.50 |
| `spin` | 4 m，4 rad/s 自转 | 0.00 | 3.62 |
| `combined` | 4.5 m，1.2 m/s + 2.5 rad/s | 0.00 | 3.88 |
| `toofar` | 7 m 静止 | 0.00 | 0.00 |

`far` 的 9.00 已经贴着武器射速上限（10 发/秒）。**这不是分数线**，
`solution` 也有它没做好的地方，清单在 `docs/reading-guide.md` 末尾。

## S0 · 检测：从像素到装甲板候选

**现状**：`vision/` 下三个函数返回空，所以一帧都检不出来。

**要写的三个函数**（约 90 行，阈值全在 `vision/config.h`）：

1. `makeColorMask()` —— HSV 范围 + 对手色通道差（红算 R−B，蓝算 B−R），再形态学。
2. `findLightBars()` —— 轮廓 → `minAreaRect` → `isValid()` 过滤 → 按 x 排序。
3. `matchArmors()` —— 两两枚举 → `Armor` 构造里已经判好几何 → 按分数排序。

**验收**：`ctest --test-dir build -R ideal_samples` 由红变绿。
它拿四张实拍正例，要求标注框对应的候选出现且 IoU ≥ 0.65。这就是你检测器的规格。

**陷阱**：

- **形态学的顺序**。灯条过曝会变成纯白，饱和度和通道差都掉到 0，mask 里只剩
  两侧各一两像素宽的彩色边，中间被挖空。这时先做开运算会把那两条细边直接抹掉，
  症状是"画面里明明有灯条，却一根都没检出"。先闭（补洞）后开（去噪）。
- **有效距离区间很窄，两头都是悬崖**：约 3.4~5.5 m。近了是过曝白洞比形态学核还宽，
  远了是灯条只有 2 px 宽、低于 `min_area`。想让区间变宽，要动的是核大小和
  `min_area` 这一组权衡，不存在一个数两头都赢。
- **曝光的影响比直觉小**。灯条是自发光，曝光从 0.4× 压到 2.5× 检出率几乎不变，
  只有压到 0.1× 才崩。先测，再下结论。
- `ideal_samples` 红了不一定是你的 bug：它同时考核"标注框对应的候选在不在"和
  "框得准不准"，先从 mask 开始一层层看。

## S1 · 距离与弹道

**现象**：你把像素换成角度、让云台指向装甲板中心，`static` 能命中，
但 `far` 一发都不中——而且误差方向是稳定的。

**为什么错**：弹丸在 5.25 m 处要飞 0.24 s，这期间掉 0.28 m，对应 2.8°；
而装甲板在 5.25 m 处纵向只占 ±0.68°。所以"指向目标"和"打中目标"差了 2° 以上。
弹丸在 4 m 掉 0.15 m（2.1°）、在 7 m 掉 0.45 m（3.6°）——**没有常数能同时满足**。

**需要什么信息**：距离。

**两条合法路径**（选一条，说清代价）：

1. `cv::solvePnP` + 已知灯条几何（小装甲间距 135 mm、大装甲 230 mm，灯条长 56 mm）；
   顺带能把相机相对云台旋转中心的安装偏移一并处理掉。
2. 用灯条视高反推：`distance ≈ fx × 灯条实际长度 / 像素长度`。
   简单，但安装偏移带来的 0.4~0.6° 系统性偏差要自己补。

**改哪儿**：`Pipeline::estimate` 里把 `estimate.distance` 填上，再用它算抬升角。
飞行时间又依赖抬升角，需要迭代几次才收敛。

**验收**：

```bash
bench/run.sh far 8      # 命中/s 从 0.00 到 1 以上（solution 是 9.00）
bench/run.sh static 8   # 不能把 4 m 的成绩做坏
```

**陷阱**：

- 6 m 以上是**检测**的极限，不是解算的极限。别指望 PnP 救 `toofar`。
- 距离估错 10%，在 4 m 处只带来 0.2° 的抬升误差，肉眼看不出来；在 7 m 处才开始明显。
  所以验收不要只看 4 m。
- 相机比云台旋转中心高 4 cm。忽略它，5 m 处就有 0.46° 的系统性偏差，
  而纵向容差只有 0.68°。

## S2 · 关联与状态估计

**现象**：每帧独立挑"离画面中心最近的那块板"，`spin` 上四块板在 90° 一圈里
轮流抢中心，指令每帧抖一次，云台是个二阶系统，抖一次要 0.2 s 才稳——追不上。

**为什么错**：没有历史，就没有速度；没有速度，就没有提前量（S3 要用），
也没有"这一帧还是不是刚才那块板"的判断。

**需要什么信息**：历史帧。

**最小可行的做法**（按顺序加，每加一步测一次）：

1. 世界系里存历史位置（不要存像素：云台自己在动，图像系里看速度不干净）；
2. 用最近几帧做最小二乘拟合，同时得到"当前位置"和速度；
3. 用预测位置做关联门限：候选离预测位置足够近才认为是同一块板；
4. 门限失败时不要死等旧板回来——立刻在新板上重开一条轨，速度沿用手上那份
   （四块板装在同一台车上，刚体速度本来就是同一份）。

**改哪儿**：`Pipeline::estimate` 的关联部分，加一个跟踪器；
`TargetEstimate::yaw_rate / pitch_rate` 填上。

**验收**：

```bash
bench/run.sh spin 8     # 命中/s 从 0.00 到 0.5 以上（solution 是 3.62）
bench/run.sh static 8   # 不能把静态靶做坏
```

**陷阱**：

- **关联门限不能是球形的。** PnP 的深度误差是 0.1~0.3 m，垂直于视线的方向只有
  几厘米。用一个球形门限的后果是"深度一抖就判换板"，历史被反复清空，
  速度永远估不出来。拆成"径向松 / 切向紧"。
- **换板次数不是越低越好。** 目标真的转到背面时必须换，卡死在一块板上会彻底跟丢。
- **不要把位置先低通再线性拟合。** 自转靶的切向在快速旋转，线性模型外推会被
  这个低通坑死（实测：加 50 ms 低通，`spin` 从 3.6 掉到 0.0）。
- 别忘了 `combined`：S2 在平移下也要稳。

## S3 · 提前量

**现象**：`translate` 一发不中，误差方向稳定——总是落后。

**为什么错**：指令瞄准的是"目标现在在哪"，但弹丸飞 0.24 s 才到，这期间靶车
已经移动了 1.5 × 0.24 ≈ 0.36 m，比装甲宽度（0.135 m）大 2.7 倍。

**需要什么信息**：距离（S1）+ 速度（S2）+ 弹速与发射延迟（`Observation` 里的
`bullet_speed`、`launch_delay`、`barrel_length`、`gravity`，从 `state.weapon` 来）。

**做法**：解一个不动点。

```text
飞行时间 t = f(距离, 抬升角)
预测位置   = 当前位置 + 速度 × (t + 发射延迟 + 流水线延迟)
t 又依赖预测位置…… 迭代几次就收敛
```

**改哪儿**：`Pipeline::estimate` 算完目标位置之后加一层预测；
再把 `yaw_rate / pitch_rate` 接进 `Command::yaw_vel / pitch_vel`。

**验收**：

```bash
bench/run.sh translate 8    # 命中/s 从 0.00 到 0.5 以上（solution 是 3.50）
bench/run.sh combined 8     # 见下面"附加题"
```

**陷阱**：

- **提前量里漏了流水线延迟。** 观测是"过去"的（取帧→检测→算出指令，十几毫秒），
  指令是"现在"发的，弹丸是"将来"到的。只补发射延迟的话，5.5 m 处的落点偏差
  实测是 5.4 cm；补上这一帧的间隔后降到 4.0 cm。
- 提前量必须用**同一帧**的观测时间，不要混用"最新状态"的时间戳。
- 弹速和延迟从 `Observation` 读，别写死——仿真 `configs/default.cfg` 里可调。
- **填 `yaw_vel` / `pitch_vel` 是白捡的分数。** 仿真的伺服是
  `a = ω²e + 2ω(goal_v − v)`，不填 `goal_v` 就有稳态滞后 `2·θ̇/ω`，
  在 4 rad/s 的自转靶上约 0.8°——比开火窗口还大。

## 附加题 · `combined`

平移和自转同时发生。

先别急着上"整车估计器"：`solution` 在这个场景拿到 3.88，靠的**不是**新运动
模型，而是 S2 里的关联策略——门限失败时立刻在新板上重开一条轨、速度沿用。
等同一块板转回来的做法在 2.5 rad/s 下要等 2.5 s，那段时间等于瞎了。

也就是说：这一档的天花板不在运动模型，而在"换板的时候你怎么处理"。
把它做对之后如果还想往上走，才轮到估"整车角度 + 角速度 + 平移速度"
（sp_vision 里"整车估计器"在做的事）——目标急停、急转时线性速度模型会失效。

## S4 · 生命周期

**现状**：`app/main.cpp` 读不到新帧时会一直重发上一条指令，包括里面的
`fire`。这在真机上就是"丢了目标还在开火"。

**怎么测出来**：不用注入故障。把 `scenarios/static.cfg` 里的 `center` 改到
20 m（或者运行中把仿真暂停），看它会不会继续发 `fire=true`。会的。

三种形态，处理方式不同：

| 情况 | 症状 | 应该怎么做 |
|---|---|---|
| 丢帧 / 断流 | 一直重发旧指令 | 超过 N ms 没有新观测就 `control=false, fire=false` |
| 仿真暂停 | 同上 | 同上，而且恢复后要等新观测，不能复用旧目标 |
| 仿真重启（`session_id` 变了） | 继续用旧会话的目标 | 清掉历史、重置序号 |

**需要什么信息**：时间、会话标识、观测年龄。

**改哪儿**：`app/main.cpp` 的主循环。

**验收**：

```bash
# 1. 目标消失后必须停火：跑起来之后把场景换成极远靶位，或暂停仿真
./build/armor_aim --fire --no-gui --duration=10
# 2. 重启仿真后不能继续用旧会话：Ctrl+C 掉仿真再启动，看客户端的行为
# 3. 有效帧率不能塌
python3 bench/report.py        # 帧率列不应明显下降
```

**陷阱**：

- 超时时间不能拍脑袋。仿真的指令看门狗是 **250 ms**，观测超时必须**小于**它。
- 帧率掉了不一定是你的错，先看"仿真/墙钟"——见开头的指标口径。

## 做完之后

`bench/report.py` 会把 `out/` 下所有跑过的场景汇总成一张表，直接贴进报告：

```bash
TAG=before bench/run_all.sh          # 改之前
TAG=after  bench/run_all.sh          # 改之后
python3 bench/report.py --out-dir out/after
```

每个阶段各自的 bench 输出、每次改动前后各一组，就是你实验记录的全部素材。
